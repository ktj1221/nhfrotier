> 원본 PDF: `docs/NH뚝딱협업스튜디오_기획안_최종개선본.pdf` (본 문서는 검색·차이 비교를 위한 텍스트 사본)

## 제안의 핵심

디자인을 잘 만드는 또 하나의 도구가 아니라, NH의 업무 맥락을 바탕으로 문서·화면을 만들고
사업·테크·디자인·준법이 함께 검토한 뒤, 결정과 변경 과정을 조직의 자산으로 남기는 **업무 제작 플랫폼**.

| 항목 | 내용 |
|---|---|
| 팀 | 농알이 / 외부 Track / 4명 |
| 인프라 | 농협은행 내부 Linux 서버 · Docker |
| AI | 승인된 LLM 서버를 인증 API로 호출 / 모델 직접 운영하지 않음 |
| 구축 방식 | 프로젝트 단위 단계적 구축 |
| 가치 | AI 제작 + NH 업무자산 + 협업 + 의사결정 추적 + 재사용 |

**한 문장 정의** — "아이디어는 빠르게 구체화하고, 협업 과정은 조직의 자산으로 남긴다."

## 1. 문제 정의와 서비스 방향

### 1-1. 현재 업무의 비효율

| 단계 | 현재 문제 | NH 뚝딱의 해결 방향 |
|---|---|---|
| 기획/제작 | 문서·PPT·웹/앱 시안을 각각 제작 | 채팅 + 참고자료 + Template 기반 동시 초안 |
| 자료 활용 | 내부 자료와 과거 산출물이 개인/부서 단위로 분산 | 프로젝트 자료와 조직 자산으로 축적 |
| 협의 | 사업·테크·디자인·준법 의견이 여러 채널로 분산 | 하나의 결과물에서 공동 검토 |
| 수정 | 반영 이유와 이전 결과를 다시 찾아야 함 | 의견 → 결정 → Version → History 연결 |
| 인수인계 | 최종 파일 위주로 전달되어 배경이 소실 | 결과물과 의사결정 근거를 함께 보존 |

### 1-2. 제품 포지셔닝

- **기존 접근**: AI 디자인 생성 / 문서 생성 / 디자인 시스템 구축
- **권장 포지셔닝**: NH 업무 제작·협의 플랫폼. 디자인 시스템은 독립 제품이 아니라 NH Template·컴포넌트·업무기준을 제공하는 "업무 자산 계층"으로 둔다.

### 1-3. 내부 환경을 고려한 원칙

- 자체 LLM을 만들기보다 승인된 사내 LLM API를 사용하고, AI 연계 계층은 서비스와 모델 사이의 추상화 레이어로 둔다.
- AI-DLC 등 기존 디자인 시스템과 경쟁하지 않고 기존 자산을 가져와 실제 업무 프로젝트에서 재사용한다.
- 폐쇄망/내부망 운영을 고려해 Linux/Docker 배포를 기본으로 하고, 향후 K8s 전환 가능한 컨테이너 구조를 유지한다.
- AI OCR, 챗봇, RAG 등 기존·향후 AI 서비스와 연결할 수 있도록 자료·API·Project 구조를 공통화한다.

## 2. 차별화 전략: "디자인 시스템"이 아니라 "업무 의사결정 시스템"

> **중요한 결론** — 협업·댓글·버전관리만으로는 차별화가 약하다. Figma는 실시간 협업·댓글·Version History를 제공하고, Claude Design도 조직 공유·인라인 피드백·디자인 시스템 적용·버전별 공유를 지원한다. 내부 AI-DLC에도 디자인 시스템과 버전/PR 중심 관리가 이미 존재한다.

### 2-1. 레퍼런스 비교

| 대상 | 이미 강한 기능 | NH 뚝딱의 포지션 |
|---|---|---|
| Figma | 디자인 제작 / 협업 / 댓글 / Version History | 디자인 파일이 아니라 "업무 프로젝트"를 관리 |
| Storybook | 컴포넌트 / 문서화 / UI 라이브러리 | 컴포넌트보다 NH 업무 Template·업무기준과 연결 |
| Claude Design | AI 디자인 / 프로토타입 / 조직 공유 / 피드백 | NH 업무자료 + 검토 + 반영 + History까지 업무 흐름화 |
| NH AI-DLC | 사내 디자인 규칙 / 컴포넌트 / 버전·PR 관리 | 기존 디자인 자산을 재사용하고 업무 결과물과 연결 |
| **NH 뚝딱** | 업무 제작·협의·자산화 | 의견 → 결정 → 반영 → Version → History → 재사용 |

### 2-2. 우리가 반드시 잡아야 할 차별점

| 차별점 | 구체화 |
|---|---|
| 업무 프로젝트 중심 | Canvas가 아니라 Project가 시작점. 사람·자료·결과물·검토·Version·History를 한 단위로 묶음 |
| NH 업무 맥락 | NH Template, 서비스별 화면 기준, 업무자료, 과거 사례를 생성 맥락으로 제공 |
| 의사결정 추적 | 댓글을 "합의 / 이견 / 추가확인"으로 구조화하고 반영 여부와 변경 이유까지 연결 |
| 과정의 자산화 | 최종 파일뿐 아니라 검토 근거·Template·사례를 다음 프로젝트에서 재사용 |
| 승인 AI 독립성 | AI Orchestrator가 모델과 서비스를 분리하여 사내 LLM 변경에 대응 |
| 내부 운영 적합성 | SSO·내부 저장소·폐쇄망·권한·Audit을 고려한 사내 전용 서비스 |

## 3. 핵심 서비스 구조

### 3-1. 서비스 모듈

| 영역 | 핵심 기능 | 핵심 질문 |
|---|---|---|
| Project Workspace | 프로젝트 / 참여자 / 권한 / 자료 | 누가 무엇을 만들고 있는가? |
| AI Studio | Chat / 자료 기반 생성 / 문서·화면 초안 | 무엇을 빠르게 만들 것인가? |
| NH Design & Template | NH Template / 나만의 Template / Asset Library | NH답게 어떻게 만들 것인가? |
| Collaboration | 댓글 / 담당자 검토 / 멘션 / 상태 | 누가 어떤 의견을 냈는가? |
| Decision Center | 합의 / 이견 / 추가확인 / 반영·미반영 | 무엇을 결정했는가? |
| Version & History | Version / 변경사유 / 행동·의견 이력 | 왜 이렇게 바뀌었는가? |
| Export & Reuse | 업무파일 / 공유 / 재사용 | 다음 업무에 어떻게 활용할 것인가? |

### 3-2. 대표 사용자 흐름

`01. 생성 → 02. 검토 → 03. 결정 → 04. 반영 → 05. 자산화`

프로젝트 생성 → 참고자료/Template 선택 → AI 초안 → 공동 검토 → AI 의견 취합 → 담당자 반영 선택 → 새 Version → 최종 파일 + History 저장 → Template/사례 재사용

### 3-3. 핵심 UX 원칙

- AI가 제안하고, 사람이 최종 결정한다. UI에서도 AI 제안과 사용자 승인 상태를 명확히 구분한다.
- 댓글은 기록으로 끝나지 않고 "반영/미반영/추가 확인" 상태를 가진다.
- 특정 Version만 공유할 수 있고, 해당 Version의 주요 결정 근거까지 확인할 수 있게 한다.
- 프로젝트 종료 후 결과물을 Asset으로 승격해 다음 프로젝트의 시작점으로 사용할 수 있게 한다.

## 4. 시스템 구성 및 AI 연계

### 4-1. 권장 아키텍처

- **사용자 영역**: 사내 사용자 → SSO → Nginx / Reverse Proxy → Frontend
- **애플리케이션 영역**: Backend API → Project / Collaboration / Template / Version / History + AI Orchestrator + Async Worker
- **데이터 영역**: PostgreSQL(업무데이터) + Redis(Session/Cache) + NFS 또는 승인 저장소(참고자료·생성파일·Version 산출물)
- **AI 영역**: AI Orchestrator → HTTPS + 인증 Token → 승인된 LLM API Gateway → LLM Server

### 4-2. 필수 설계 원칙

| 원칙 | 설계 내용 |
|---|---|
| LLM 직접 호출 금지 | Browser가 LLM을 직접 호출하지 않고 Backend/AI Orchestrator가 호출 |
| 인증정보 보호 | Token/API Key는 Frontend에 노출하지 않고 서버 측 보안 저장 영역에서 관리 |
| 비동기 처리 | 대용량 파일·장시간 생성은 Job으로 처리하고 상태/재처리 관리 |
| 파일/DB 분리 | DB는 메타데이터, 실제 문서·이미지·Export 결과는 파일 저장소에 보관 |
| 모델 독립성 | 서비스 API와 LLM 모델을 분리하여 승인 모델 변경 영향 최소화 |
| 운영 확장성 | 초기 Docker Linux 배포 → 향후 K8s 전환 가능한 컨테이너 단위 설계 |

### 4-3. 내부 AI 생태계와 역할 분담

- **AI-DLC**: 기존 디자인 규칙·컴포넌트·개발 가이드를 재사용하고 중복 구축을 피한다.
- **AI-Driven / AI OCR**: 공통 AI 환경 및 OCR 결과와 연계하되 역할을 분리한다.
- **RAG**: 업무기준·VOC·사례 확대 시 선택적으로 검색·생성 계층을 추가한다.
- **SSO·폐쇄망·Docker/K8s**: 사내 인증·접근통제와 초기 Docker 배포, 향후 K8s 전환을 고려한다.

## 5. 개발 프로젝트 분할

> **개발 전략** — 서비스를 한 번에 만들기보다 공통 기반 → NH 업무자산 → AI 제작 → 협업/의사결정 → Version/자산화 순으로 분리한다. 각 Project는 독립 데모와 검증이 가능해야 하며 선행 결과물을 후속 Project가 재사용한다.

| Project | 목표 | 핵심 개발 | 완료 기준 |
|---|---|---|---|
| P1. 업무공간 | 서비스 골격 | SSO / Project / 권한 / UI / DB / 파일 / Docker | 로그인 후 Project 생성·자료 등록·조회 |
| P2. NH 업무자산 | NH 특화 맥락 | NH Template / 서비스별 Template / 나만의 Template / Asset Library | Template을 선택해 일관된 결과물 생성 |
| P3. AI 제작 | AI 초안/시안 | Chat / 참고자료 / LLM API / AI Orchestrator / Async Job | 승인 LLM API로 문서·화면 생성 |
| P4. 협업·의사결정 | 공동 검토 | 댓글 / 검토상태 / AI 의견 취합 / 합의·이견·추가확인 / 반영선택 | 여러 담당자가 하나의 결과물을 검토하고 결정 |
| P5. Version·자산화 | 과정과 결과 연결 | Version / History / Diff / Audit / Export / 재사용 / RAG 검토 | 변경 근거 추적 + 결과물 재사용 |

### 5-1. MVP 범위

| MVP | 후속 고도화 |
|---|---|
| Project / SSO / 파일 / 기본 권한 | 정교한 조직권한 / 결재 연계 |
| NH Template 기본 세트 | Template 추천 / Marketplace |
| Chat + 승인 LLM API | 다중 모델 라우팅 / Agent Workflow |
| 기본 댓글 + AI 의견 취합 | 고급 Workflow / 실시간 공동편집 |
| Version + History + 기본 Export | 고급 Diff / Audit Analytics / RAG |

**권장 개발 순서: P1 → P2 → P3 → P4 → P5**

## 6. 데이터·이력·업무 자산화

### 6-1. Version과 History를 분리

| 구분 | 정의 | 예시 |
|---|---|---|
| Version | 공식 결과물의 변경 단위 | v1 최초 생성 → v2 사업 의견 반영 → v3 준법 의견 반영 |
| History | 행동·의견·AI 처리·의사결정 과정 | 댓글 → AI 취합 → 반영 선택 → 수정 → v3 생성 |
| Audit | 접근·권한 등 주요 운영 행위 | 로그인 / 프로젝트 접근 / 권한 변경 / AI 요청 |
| Asset | 향후 재사용 대상 | Template / 업무사례 / 결과물 / 검토 기준 |

### 6-2. 핵심 데이터 관계

```
USER → PROJECT → DOCUMENT → VERSION
PROJECT → MEMBER / COMMENT / REVIEW / HISTORY / AUDIT / TEMPLATE
VERSION → FILE → EXPORT RESULT
```

> **업무 자산화의 차별점** — 프로젝트 종료 시 최종 파일만 보관하지 않고, "어떤 Template을 사용했고 / 어떤 의견을 반영했으며 / 왜 변경했는지"를 함께 저장한다. 다음 프로젝트는 과거 결과물을 그대로 복사하는 것이 아니라, 검토 근거와 Template까지 재사용할 수 있다.

### 6-3. 핵심 화면 예시

| AI 협의 정리 | 상태 |
|---|---|
| CTA 위치 상단 이동 | 합의 완료 → 반영 |
| 상품 비교 기준 | 의견 조율 필요 → 담당자 선택 |
| 우대금리 표현 | 추가 확인 → 준법 검토 요청 |
| 최종 결과 | v4 생성 → History 자동 기록 |

### 7-2. 주요 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 기존 디자인 시스템과 중복 | 기존 시스템 대체가 아닌 상위 업무 레이어로 정의 |
| Claude/Figma와 차별성 약화 | NH 업무맥락·의사결정 추적·자산화에 집중 |
| AI 품질 편차 | Template·참고자료·검토·승인으로 보완 |
| 내부정보 유출 | 내부망·서버측 인증·접근권한·보존정책 적용 |
| LLM 변경·장시간 처리 | AI Orchestrator + Async Job으로 대응 |

### 7-3. 개발 전 확정이 필요한 사항

| 영역 | 확정 질문 |
|---|---|
| 승인 LLM | API endpoint / 인증 / 모델 / 호출한도 / Timeout |
| Infra·Storage | Linux/Docker 사양·운영방식 / NFS 등 저장소 / 용량·보존기간 |
| Security | 입력자료·AI 로그 저장범위 / 마스킹 / Audit 정책 |
| 권한·RAG | Owner/Editor/Reviewer/Viewer / RAG 대상과 검색 인프라 |
| Export | HTML / PPTX / DOCX / HWPX 우선순위 |

> 7-3의 "영역" 열 일부는 원본 PDF에서 표 좌측이 잘려 인쇄되어 있어, 문맥에 따라 복원한 값이다. 원본 확정 시 대조 필요.
